大模型写小说与 Coding 的区别

上下文爆炸、内容漂移、文风问题

用三类问题解释长篇续写为何需要额外的状态管理与验收，再对照 Coding 的工具反馈，展示 SQLite 的实际表结构节选与本 Skill 的应对流程。全稿八页。 这里比较配合工具的 Coding 与缺少独立核验的小说续写流程；代码也可能漏测，小说也可以加入检查。重点是工作方式，不是模型能力排名。

01 · 长篇写作的难点

长篇连写，三个问题越来越突出

上下文爆炸

设定、正文、档案持续叠加
全书反复输入，成本上升
只留近期，又容易漏依据

内容漂移

认知、动机与事实前后冲突
伏笔丢失，成长缺少依据
错误继续被后章沿用

文风问题

叙述口吻前后变化
不同人物说话同腔
套话与重复解释逐渐增多

长篇需要持续管理历史、因果与声音。

风险归纳：context-runtime / characters / editorial02
上下文爆炸指材料与重复传递不断增长，不是声称算法或费用按指数增长。例如 100 章、每章 3000 字，正文已约 30 万字，再加入设定、人物档案和聊天历史，若每次无差别重读，准备与传递会持续增加。只按字数截断或只取近期，可能遗漏当前选择依赖的早期经历。实际 token 与费用需要宿主账单，不能以字符直接换算。 内容漂移包括人物提前知情、动机突变、资源或时间矛盾、伏笔与成长未兑现；文风问题包括叙述声音变化、对白同腔、句式与解释反复。三类都是需检查的风险，不保证每次连写都会发生，也不给出未经测量的发生率。 依据：references/context-runtime.md、characters.md、editorial.md。

02 · 流程对比

Coding 的优势：外部反馈能反复验证

Coding工具辅助

  1. 定位代码源码与依赖
  2. 生成改动实现需求
  3. 运行检查编译、测试、运行
  4. 审查结果行为与体验

发现问题：修正后重新验证

小说续写缺少独立核验

  1. 整理上下文摘要、档案、按需加载
  2. 生成新章依赖当前材料
  3. 缺少核验因果与文风未验
  4. 继续沿用后章据此展开

继续生成：漂移与文风问题可能累积

代码也会出错，编译与测试让部分错误更容易暴露。

依据：Anthropic · Coding agents · 小说风险为流程示意03
上行是带工具反馈与审查的 Coding；下行示意只做提示、摘要、档案或按需加载，未加入历史核对和独立审稿的常规 Skill。这里按工作机制比较，不声称所有其他 Skill 都缺少核验。 摘要与检索能缓解上下文膨胀，但整理材料本身不验证材料真假。摘要若记错人物所知或关系，新章仍可能沿用错误；生成后没有对照历史正文核验，就无法可靠发现内容漂移。反复生成不是验证。 Coding 常能借助源码定位、编译、测试和运行获得部分外部证据，但复杂依赖、需求与体验仍需审查。小说中的人物因果与文风需要读正文、核对历史和风格来源，模型说“已检查”不能替代真实审稿。 工程参考：https://www.anthropic.com/engineering/building-effective-agents 长故事参考：https://aclanthology.org/2022.emnlp-main.296/ 比较的是工作条件，不推断内部训练原因，不外推百万字质量。

03 · 常规 Skill 的边界

常规 Skill：管住上下文，仍会漂移

上下文管理

  1. 保存材料正文、设定、档案
  2. 提炼摘要减少历史复述
  3. 按需加载选取当前相关材料
  4. 继续写作使用整理后的上下文

缓解上下文爆炸

减少全书反复输入
保留当前任务需要的材料

内容漂移仍需检查

摘要记错，错误也会被沿用
材料齐全，新章仍可能偏离

上下文变小 ≠ 内容正确。整理材料之后，还需要核验。

这里指以摘要与按需加载为主、尚未加入独立内容核验的 Skill04
这一页按机制区分上下文管理与内容一致性，不对所有 Skill 作一概判断。常规 Skill 在此特指以提示、摘要、档案和按需加载为主的流程；它们可以缓解上下文膨胀，但仅凭整理材料不能可靠解决内容漂移。若其他 Skill 已包含持久状态、证据核对与独立审稿，也具备相应治理能力。 例如摘要把“怀疑”写成“知道”，即便材料变短，后章仍可能沿用错误；即使摘要准确，生成的新章也可能让人物突然无条件信任他人。因此检索既有材料与检查新章是否成立是两项工作。 按需加载也不能为了缩短输入而删去必要因果依赖，疑点须回查历史正文。来源：references/context-runtime.md、continuity.md、editorial.md。

SQLite：人物状态怎么记

events 表 · branch=main / chapter=18 / idx=0
示例：林舟对沈砚的关系变化 · 以下展开 data 内的 JSON 字段

明细字段示例值作用
data.opstate记录人物状态变化
data.entityC01（林舟）稳定 ID，改名也能追踪
data.keyrelation:C02（沈砚）标明对谁的关系

data.evidence.start128（字符偏移）定位第 18 章的证据

按人物取材，核对“前值 → 后值”，用正文证明变化。

实际存储：events.data（JSON） · 演示值 · 当前状态由事件重放得到05
此页展示真实 events 表中一条 state 事件的 JSON 明细，不新增或声称存在独立的人物状态 SQL 表。events 的实际列为 branch/chapter/idx/data/prev_hash/hash；data.op、data.entity 等是 JSON 路径，不是独立 SQL 列。完整示例事件还需 data.evidence.chapter=18；本页省略哈希等字段。 人物名、ID、关系值、引文及字符偏移均为演示数据，不是项目中的真实小说记录。假设 C01、C02 已登记，第 18 章提交前 C01:relation:C02 的状态为“警惕”；本章事件 after 为“有限信任”。关系属性采用 continuity.md 建议的 relation:对方ID。伤势、动机等也可用 state 事件记录，属性名须在项目内保持一致。 程序验证 before 与此前重放得到的状态一致，并核对 evidence 的章号、字符位置和原文。事实审稿还需判断引文及上下文是否足以支持关系变化，匹配字段不能代替语义审稿。按人物与依赖检索当前状态及相关历史，减少每章重复加载全书。 人物所知另用 knowledge 事件，区分知道、相信与怀疑；人物声线保存在 meta 的版本化人物档案中，属于设计和解读，不作为已发生事实。文风问题仍通过风格锚点、声线材料与读者审稿复核。 来源：scripts/novel_core/store.py、ledger.py、characters.py；references/continuity.md、characters.md。

04 · 本 Skill 的核验

内容漂移：保存状态之后，还要核验

第 18 章 · 已成立

林舟对沈砚：有限信任
“这一回，我信你。”

第 19 章 · 候选稿疑点

林舟向沈砚坦白全部秘密
是否有新的动机与事件支持？

核验与返修

  1. 读人物前态状态与相关正文
  2. 事实审稿核对变化与因果
  3. 返修疑点补足或调整情节
  4. 重验再入库通过后更新状态

SQLite 留下核对依据；审稿判断新章变化是否成立。

演示情节 · 状态前值由程序核对，变化依据由事实审稿检查06
沿用上一页的演示人物与关系状态，并非真实小说数据。有限信任后坦白秘密不必然是错误，关键是新章是否通过具体事件、动机与场景给出足够支持；审稿要回查正文，不能只根据状态标签机械否决。 state 事件的 before 即便正确，也不说明 after 的语义合理。程序核对前值、证据定位等结构条件；facts 独立读取人物所知、关系变化与历史因果，检查候选正文能否支持这次变化。若有疑点则返修、重新审稿，通过正式提交后才更新有效账本。历史修订还需重验受影响后文。 认知、资源、时间与伏笔也需要相应核验。SQLite 是持久化依据，审稿是判断环节，二者结合仍不自动保证文学质量。来源：scripts/novel_core/ledger.py；references/continuity.md、editorial.md、repairs.md。

04 · 本 Skill 的核验

文风：叙述口吻与人物声音分别检查

叙述口吻

保留作者确认的风格样例
对照句式、节奏与用词
检查前后文是否变调

人物声线

记录各人的表达习惯
区分对谁说、为何这样说
声音变化须有成长依据

读者审稿

核对实际正文与样例
检查对白同腔、套话重复
指出疑点，返修后再审

事实前后一致之后，还要检查声音是否符合人物与场景。

风格锚点与人物声线按配置启用 · 检查以实际正文为准07
叙述文风与人物对白分开准备依据。存在 style_anchor 时，reader 核对作者确认的 traits 与 sample，检查叙述口吻、句式节奏和用词；启用 profiled 人物模式时，以版本化人物 voice 及场景意图检查对白身份。人物档案是设计和解读，不当成已经发生的世界事实。 检查不等于固定模板或机械重复口头禅。面对不同对象、处于不同压力或经历成长，声音可以合理变化；审稿要检查变化是否符合场景与历史依据。language/repetition 与跨章复核还用于发现重复解释、同款收束和文风漂移。 这些流程支持发现和返修问题，不保证文学质量。来源：references/characters.md、editorial.md、voices.md。

05 · 创作流程

让长篇也形成反馈闭环

小说流程

  1. SQLite 账本正文、状态、文风
  2. 按需取材当前场景与依赖
  3. 执笔与双审事实＋读者
  4. 正式入库版本与进度

通过审稿：成果与依据写回账本；未通过则返修

中断可续
任务与输入持久化
恢复当前任务继续执行

修订可追溯
保留旧稿、版本与审稿证据
重验相关后文

账本保留依据，审稿发现漂移，返修后再验收。

novel-ledger-v2 · 持久状态、按需取材、独立审稿与修订复核08
图中的入库返回线表示已通过的正式成果写回账本。未通过的候选稿也会保留，但不能当成已发生事实；它走返修，再重新事实与读者审稿。首章口吻与重大约定由作者决定。 SQLite 保存任务状态和输入，中断后从当前任务恢复。连续运行依赖宿主与调度，不承诺关闭聊天后后台自动续写。局部补丁与历史修订保留旧版本和证据，受影响后文继续复核。 完成一章或通过形式检查不代表全书质量，跨章、卷末与完本仍核对因果、成长、承诺与文风。 来源：SKILL.md、references/runtime.md、editorial.md、repairs.md。
