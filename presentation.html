03 · 发现问题，与 Coding 的区别

写得出来，长篇仍会出问题

遇到的问题AI Coding 的工作条件长篇写作的难点
历史越来越多按源码结构定位相关依赖人物经历与关系散落在正文中
事实与动机漂移编译、测试暴露部分错误文字流畅，也可能存在因果错误
文风与对白同质化部分行为可重复验证人物声音与阅读体验需要读正文

例如：“怀疑凶手”在摘要里变成“知道凶手”，后文开始沿用错误前提。

长篇写作需要跨章核对，生成流畅只是验收的一部分。

问题归纳：context-runtime / continuity / editorial03
这里合并问题现象与 Coding 的工作条件。代码与小说都可能出错，但反馈依据不同。 历史增长后，全量重读增加成本，只保留近期又可能遗漏行动前提。代码有源码和调用结构辅助定位，小说的重要经历与认知散落在正文里，需要显式取材和核对。 例如摘要将怀疑写成知道，会改变后续行动的前提。有限信任突然变成全部坦白，也需要新事件、动机或代价来支持。 编译与测试能暴露部分代码问题，但仍会漏测。小说文字流畅时也可能有因果错误；人物声线、节奏与阅读体验则需要对实际正文作判断。 长上下文不能单独保证取材正确，模型自称已检查也需要证据。下面讲怎么把状态与反馈纳入 Skill。

04 · 对应解决思路和设计

解决思路：让创作有依据、有反馈

面对的问题设计选择要得到的效果
历史太多保留原文，按当前任务取材减少无关重复，疑点可回查
事实漂移显式记录变化，绑定正文来源有前态、有后态、有依据
自检容易漏判执笔与审稿分开，返修后重验独立反馈，候选结果先验收

作者确定看点、终局和文风；计划给出方向，正式正文确立事实。

模型完成创作与语义判断，脚本和账本管理状态与提交。

设计依据：SKILL.md / context-runtime / editorial / continuity04
这一页讲为什么选这些机制，下一页讲职责如何落到具体组件。 历史太多时，按人物、话题与必要历史依赖取材，保留完整语义单元和原文回查通路，减少无关重复而不是截掉必要因果。 事实漂移时，区分未来计划、候选稿与正式正文，记录状态变化和来源。程序核对前态与引用，审稿判断变化的语义依据。 自检缺少反馈时，将执笔、事实审稿和读者审稿分成独立会话。新稿先作为候选，发现缺陷就返修重验，通过后才更新正式状态。 作者确定创作约定，分层规划安排全书、分卷与近期章节。跨章、卷末和全书复核检查成长、伏笔与终局，历史改变后复核受影响后文。 脚本能核对结构和完整性，文学判断仍靠审稿与实际阅读；审稿者也可能漏判。

05 · Skill 的架构设计

Skill 架构：谁负责什么

Skill 文档

规定创作流程、阶段职责与提交协议。

AI 主控会话

获取任务，委派独立会话执行，确认提交后继续推进。

Python ＋ SQLite

脚本准备材料、校验提交；账本保存正文、事件、任务与版本。

模型 Worker

完成规划、执笔或审稿。执笔、事实审与读者审分别执行。

主控调度，脚本校验，账本留存，模型完成当前任务。

架构依据：SKILL.md / runtime.md · engine.py / store.py05
这一页把此前笼统的“系统”具体展开成四个职责。 Skill 文档约定怎么做，包括创作规则、阶段指南与提交契约。作者约定另存账本，并持续带入任务。 AI 主控会话调用脚本获取当前任务，再通过宿主工具委派新模型会话。它确认真实提交后再获取下一项任务，不把启动成功当完成。 Python 脚本负责状态机、材料组织和形式校验，SQLite 保存正式正文、候选稿、事件、任务输入、回执与分支。next 本身不会启动模型，需要主控实际派工。 Worker 只完成本次任务。写作、事实审稿和读者审稿使用不同空历史会话，事实审核对因果，读者审先读正文再核对约定。独立性依赖宿主历史隔离能力。 一个项目同一时间只有一个有效 pending，连续章节串行推进。中断从持久状态恢复，历史修改走候选分支复核，持续执行需要宿主调度。 下一页用 events 表说明账本如何保存变化与正文证据。

06 · 数据的结构设计

events 表：把状态变化与正文证据一起保存

SQL 表结构

字段类型含义
branchTEXT所属正文分支
chapterINTEGER发生在哪章
idxINTEGER章内事件顺序
dataTEXT事件 JSON
prev_hashTEXT前一事件哈希
hashTEXT本事件链哈希

复合主键：(branch, chapter, idx)

data：一条关系变化事件

{
  "op": "relation",
  "from": "C01", "to": "C02",
  "key": "trust",
  "before": "警惕",
  "after": "有限信任",
  "evidence": {
    "chapter": 18, "start": 128,
    "quote": "林舟收起刀：这一回，我信你。"
  }
}

关系有方向，变化有前态，结论有正文来源。

程序核对前值、引文和事件链，审稿判断变化是否有充分依据。

实际表结构：store.py / ledger.py · JSON 内容与字符位置为演示值06
用一张实际的数据表说明前面的设计思路。events 的六个 SQL 字段与项目初始化定义一致，复合主键是 branch/chapter/idx。 branch 让候选修订分支与正式版本分开；chapter 和 idx 标明事件顺序；data 保存具体事件。关系、人物认知、资源与承诺使用不同的 op，但共享顺序和证据结构。 右侧展开 data 里的 relation 事件。C01 为林舟，C02 为沈砚，表示林舟对沈砚的信任变化，不表示双方的信任必然对称。两端须已注册，before 须匹配此前重放得到的关系前态。 evidence 的 chapter、start、quote 将变化绑定到正文。start 是 Python 字符位置，不是 UTF-8 字节位置。人物、引文与偏移为演示数据，例子不是可以直接提交的真实结果。 prev_hash 与 hash 形成事件链，用于完整性核对，不能证明文学因果合理。程序核对前态和精确引用，事实审稿读取必要语境，判断引文是否充分支持变化。 状态由事件重放得到，候选稿和计划分别存储。正式正文和事件只在两审通过、程序校验完成后更新。正文版本和引用需要保持一致，历史修订时受影响的事件和审稿也要重建。 这里强调三个设计选择：状态变化显式记录，事实结论保留来源，程序校验与语义审稿分工。完整性校验不能代替阅读判断。

07 · 懒人写作

懒人写作：没有设定也能开始

发起开书即可开始，无需预先准备题材、大纲或人物设定。

  1. 开始开书还没想好写什么
    也可以发起
  2. 挑选方向每轮 2～3 个候选
    包含可落地的脑洞
  3. 补全设定逐步选人物与规则
    形成创作约定
  4. 试章定调先看实际正文
    作者确认方向与口吻

少写提示，多做选择

回复 A / B / C，或说“换一组”
Skill 引导问题，整理选择

脑洞有生成方法

混搭设定、反转规则、加入代价
换一组时切换构思方式

把开书前的准备，变成逐步选择和试写反馈。

功能依据：creation.md / hatch-ideas.md07
前半段讲长期创作怎样得到依据和反馈。第二个重点是开书体验：没有题材、主角或大纲，也能发起开书。 这里的“无需输入”指无需预先提供一整套小说内容。发起开书后，Skill 先给候选并引导选择，作者仍参与方向选择和首章定调。 缺方向时，每轮只推进一道选择，给 2～3 个因果不同的候选，含至少一个可落地的高概念脑洞。作者可以回复 A/B/C、换一组、自定义或返回。 选择链从读者承诺和推进引擎开始，逐步确定主角、核心关系、世界对抗、机制、终局、体量文风。选择结果整理成创作约定，后续再进入全书、分卷和近期章节设计。 首章通过两审后交作者确认，认可后才定调。试章不喜欢可以提出修改，模型不替作者批准。 这一页讲的是现有 Skill 的交互设计，不声称无需发起请求或无需任何作者选择，也不承诺关闭聊天后自行运行。 【脑洞方法，按需展开】 这一页用分享用的示例构想说明脑洞方法，不把它冒充项目已有小说或实际生成结果。 创意工具箱包含高概念混搭、倒置公理、不可逆代价、限制驱动、认知差、规则推演、对抗绑定和终局闭环等方法。 以记忆作为货币为例，先让交易机制进入调查情节，再加入支付自身记忆的代价，继续推演到社会结构。这些选择让设定产生冲突与长期抉择，后续还需规划并用正文验证。 候选要因果不同，说明收益、代价与风险。作者说换一组时切换方法，避免只改名字和数字。脑洞也用于卷纲方向与关键转折，选定方向保留理由。 这次分享的两个重点到这里合在一起：没有预设题材也能由候选引导开书，形成方向后再靠账本、取材和独立审稿支撑长篇迭代。 最终好不好看仍需读实际正文，审稿也可能漏判。作者保留方向与首章的决定权。

演示顺序 · 开书交互与已准备项目分段展示08
现场分两段：从没有题材的请求开始，展示候选与换组；再打开事先准备的项目，展示正文与可回查的事件。 开场示例：“用 novel-ledger-v2 帮我开一本新书，还没想好题材。”不预填世界观或人物，让 Skill 按开书选择链给方向。展示 2～3 个因果不同的候选，接着说换一组，观察是否切换构思方法，而不只是改名字。 选一个方向继续，让大家看到后续问题如何把看点、推进引擎、人物与规则逐步补全。首章试写需要完整创作约定，作者仍负责定调。 正文部分使用预先准备的小说项目，打开 book.html 和首章，找一条带正文证据的事件，对照前态、后态与引文。明确这是已有项目，不把预先准备的成果说成刚刚生成。 演示前检查 Skill 可用、项目路径正确、阅读视图可打开，并准备备用截图。未提前准备正文项目时先展示开书与候选，现场内容按实际结果说明。 这一页是演示顺序，不代表已经执行了现场开书。最终回到两个重点：开书省准备，长篇过程有依据、有反馈。
