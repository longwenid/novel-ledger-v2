# 局部返修与安全文本补丁

## 小问题只写修改部分

能明确定位且不改变整章因果结构的问题，优先局部返修：错别字、地址误写、一处重复说明、一段对白同腔、遗漏的短动作或不通顺的衔接。审稿 fix 时增加 `repair_scope: "local"`，findings 仍须给精确正文位置、读者影响和修订目标。

涉及全章动机、视角、结构或多处因果重排时用 `repair_scope: "chapter"`。省略则沿用整章上下文。不要为了节省 token 把结构问题标成局部，也不要把“先改一点看看”当成完整修复方案。

局部 repair 输入包含相关原文及相邻段落、绝对字符范围、基稿哈希和省略字符数；不重复传入整章正文及全书未来设计。核心约定、有关当前事实、人物档案和必要历史仍保留。段落以正文换行分隔，长段不会被静默切碎；如果全章只有一大段，局部输入也可能覆盖全章。

## 提交补丁

信封不变，data 例如：

```json
{
  "base_hash":"复制本次 payload.base_hash",
  "patches":[
    {"start":123,"old":"办公室在三楼505。","new":"办公室在四楼101。"}
  ],
  "repair_note":"恢复既有地址，其余段落不变"
}
```

start 是**完整基稿的 Python 字符位置**，不是片段内位置、UTF-8 字节位置或“第几段”。使用输入 excerpt.start 加片段内精确位置计算；引文 old 必须与该位置完全一致。所有补丁针对同一个基稿，不能把前一个补丁造成的位移计入后一个 start。

- `patches` 非空，每项恰为 start/old/new。old 非空；插入新句时连同邻近原文作为替换锚，不能对空字符串插入。写成 `{start,end,text}` 的区间替换形式会被自动换算为 start/old/new（old 即该区间原文），区间越界或为空不换算、按 `patch` 报错。
- 可以删除某段（new 为空），但不能清空整章。
- 不允许重叠补丁、原样替换、错误哈希或错位原文。重复出现的相同句子依靠 start 精确定位，只改目标位置。
- 局部任务只能改已提供 excerpt 范围内的文本。工具先验证全部补丁，再从后往前合成；任一失败则原任务、草稿和正式稿均保持不变。
- 一次提交在 prose/patches/reuse_original 中只能选择一种。局部 repair 不接受整章 prose。

输出补丁不代表正式稿已更新。工具先生成新的完整候选章，再重新派发 facts 和 reader，重新抽取事件、摘要和正文证据；不能复用旧审稿回执或旧字符位置（引文 start 漂移且原文唯一时可被自动重定位，见 [结果协议](protocol.md)）。原任务回执与不可变基稿快照保留在 SQLite，重复 submit 幂等。

**返修后的事实重登记是全量的**：返修/重设计清空本章已登记事件，随后 facts 任务的 payload 会带 `prior_events`。v1.9 起引擎**自动续算**证据仍唯一命中新正文的前序事件（`auto_carry`，回执 events 只写新增/变更，重复提交会被拒）；证据断裂的事件须以 `prior_dispositions` 声明 dropped/replaced 及理由，也可用同样声明覆盖自动续算。静默丢弃会被 `event_accounting` 拒绝——这是防止账目悬空的硬护栏；审稿检查仍覆盖整章，自动续算只省去机械重打。

## 需要更多上下文时

按任务 ID 分段读取原候选，避免把尚未验收的稿件误当成 recall 返回的正式正文：

```bash
python3 "$ROOT/scripts/novel.py" candidate --project "$PROJECT" --task TASK_ID --start 0 --end 2000
```

start 包含该字符，end 不包含该字符，范围与 Python 的 `[start:end]` 一致。返回本任务不可变基稿及基稿哈希；默认一次最多 4000 字符，可显式指定至最多 16000 字符，报告前后省略量。任务完成后仍可查询该版本。`candidate` 只读取材料，不扩大允许修改的范围。

若还需改动未提供的段落，局部 repair 可提交：

```json
{"expand_context":true,"reason":"地址修正涉及章首的进楼路线，需一起检查"}
```

工具保留草稿及返修次数，生成含完整正文的 repair 任务；再次请求扩大不被接受。整章上下文任务仍可只输出 patches，只有确需重写时才输出 prose。两轮修订与一次 redesign 的上限不变；扩大上下文不能重置失败计数。redesign 是设计重写，提交完整 prose 与 design_change。

## 已有正文修订

必须先走 revise 建立候选分支。该分支 draft 有原稿时，提供 base_hash；可提交同样的 patches/repair_note，不必重发整章。后续某章经核对无需改变，可提交：

```json
{"base_hash":"本任务原稿哈希","reuse_original":true}
```

这仅复用正文字符，仍重新抽取事实与审稿，不把“不改文字”当成“不受前文影响”。新写首稿没有基稿，不接受补丁或复用；已发布正文的冻结规则不变。候选全部验证前，正式分支不变。

## 实际节省与边界

主要节省返修 agent 的整章重复生成；局部模式还减少其读取的当前章文本。事实与读者审查仍读取合成后的完整章节，避免漏查牵连；本版不冒险用局部通过替代全章验收。

报告字符数和 JSON 体积可衡量重复文本减少量，但不能当成实际模型 token/费用记录。没有外部模型计费数据，不承诺具体节省比例。正确性与阅读质量判断保持原标准。
