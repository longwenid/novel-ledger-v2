## 交付结果

已实现可独立使用的 Skill、十二份按需参考、Python 标准库控制工具、项目/驱动模板、工程测试及真实创作样本。命令支持开书、定调、逐阶段任务、检索、当前/历史局部地图、审计、滚动规划、候选修订、通用驱动、暂停恢复、导出和完本。

正文及事实以 SQLite 为唯一持久化真源。计划、事实、认知、摘要分层保存；资源精确计算并检查前态；核心阅读检查必须有正文证据。审稿中的实质质量问题可触发返工，不限于客观格式错误。

这是一套提高连续性和创作质量的工作方法与工具，不是优秀小说的自动证明器。

## 发布后上下文压力排查

对 v1.4.1 新增每组 1000 章、每章 3000 字符的合成压力测试，已复现人物认知/积压伏笔导致工作包超限，且 resume 后再次超限；另发现紧凑 JSON 预算小于实际格式化输入文件的计量差异。该结果记录 v1.4.1 的历史缺陷。详见[排查报告](context-stress-report.md)与[原始结果](context-stress-results.json)。该排查当时未修改生产实现或旧发布包。后续 v1.5.0 已按持久层、材料准备和有界任务三层修复，并增加会话交接；五组千章合成历史均可继续提交第 1001 章，详见[架构修复验收](context-architecture-fix.md)。真实宿主窗口和文学质量未因此视为已实测。

## v1.1 空间与稳定事实增强

新增 [分层场景管理与事件协议](../references/spatial-continuity.md)、[可运行约定](../assets/spatial.example.json)及 [实际导出地图](spatial-map.md)。普通场景保留最小定位信息，常驻场所登记布局，复杂行动补通行/感知条件；无需给所有一次性场景编造完整地图。

工程检查覆盖：

- 第一章通过正文证据建立“四楼101的局长办公室”，第二章无变更写成“三楼505”时，空事件不能绕过已生成的地址核查提示；错误稿未进入正式章节。
- 物理房间与办公室用途分别建模；合法搬迁保留旧房间，重编房号保持物理 ID，历史地图返回对应章末地址。
- 稳定出生日期等锁定事实不可普通改写；楼层继承、房号、别名对应的同一地点、位置唯一性与携带链得到验证。
- 关闭的门、未知路径、耗时不足、先后移动重叠、不可见与未登记声音通道均不被默认通过。
- 地图与来源进入必需工作包；预算不足会明确失败，不悄悄删除布局。

独立端到端验证曾发现三处可正式提交的漏洞：anchor 另建矛盾位置、经未定位持有者转手绕过路线、携带物落地后丢失时间下限。修复后独立复测全部在 facts 阶段拒绝且无半提交；正常交接和接收者后续移动可正式提交并通过 audit。[独立验证记录](spatial-independent-review.json)保存实际覆盖与边界。

明确未实现的能力：任意自然语言空间矛盾自动识别、完整几何/物理模拟、历法和年龄自动求解。跨句“他走进局长办公室。这屋在三楼，门牌是505”可能没有词法提示；模型若漏审并提交虚假的 pass，工具不能证明正文语义正确。因此指南强制事实审稿主动比较原文、指代与当前地图，不能把引文存在或 audit 成功当语义证明。

v1.1 重新审计现有《借火簿》12 章和《夜班退件》1 章，均无问题；未把这些旧样本冒充新增地图机制的文学效果测试。本次空间用例是工程与流程验证，尚无全长小说空间漂移率的统计结论。

## v1.2 分层世界设计与子 agent 任务书

新增 [分层设计指南](../references/design-and-brief.md) 和 [可提交的设计样例](../assets/design.example.json)。新书模板启用 layered：全书世界设计 → 当前卷准备 → 近期场景计划 → 既有写作审稿闭环。每批章计划仅覆盖已准备的当前卷；卷末结束本批，下一卷先经过设计准备。

设计由 SQLite 保存修订号、任务回执、哈希及历史依赖，始终标记为未来提案，不自动入事实账本。设计重做保留旧版本；正文修订会使受影响设计和后缀计划重新检查，正式分支在候选晋升前保持可查询。未启用 layered 的已有书保持原任务流程。

写作输入自动生成 writer_brief 和 Markdown 场景任务书，包含读者体验、人物选择、冲突、必要变化、场景提案、当前站位/认知及材料指引。具体台词和动作留给执笔；事实审稿不接收该任务书与设计全文，读者首读不接收计划、作者约定、状态或设计。

[实际任务书示例](layered-brief.md)、[完整机器输入](layered-input.json)及 [生成范围记录](layered-example.json)来自真实 CLI 准备流程。示例停在 draft，未把准备材料当作已经写出的小说。

独立前向验证实际执行 121 次 CLI 调用、41 次成功提交，覆盖两卷完本、卷审先于下卷准备、正文修订晋升、设计历史、必需历史全文、角色材料隔离及派生任务书重建。[当时的完整调用记录](layered-cli-log.json)保留了修复前的复现结果。验证发现两处问题：卷末后同批继续同卷，以及 draft 的 plan_update 被接受但忽略。前者增加卷末位置约束；后者明确仅 redesign 支持，其他阶段拒绝。回归用例纳入 67 项工程测试；独立复测也确认两项均被拒绝、原任务和事实保持不变，随后合法提交可继续。[复测日志](layered-retest-log.json)。

本次两卷闭环使用合成工程审稿回执，验证阶段控制和数据边界，不声称增加了真实文学质量试验，也未实际接通外部模型。原有真实创作样本仍保持下文所述覆盖；v1.2 对其账本重新审计通过。自由文本设计里的因果和事实语义仍需规划者及审稿者判断。

## v1.3 人物小传与对白差异

新增 [人物档案指南](../references/characters.md) 和 [结构化人物样例](../assets/characters.example.json)。新模板启用 profiled：章计划后按实际出场人物准备缺失或失效的档案，再交给写作。小传包含身份、诉求、经历与主要人物的内在矛盾；表达习惯区分关系对象与压力；场景计划给每个拟发言者独立的目的、隐瞒、压力和策略。静默场景可明确不安排对白。

档案属于设计与有来源的解读，不能制造客观事实。已确立经历和代表性对白须引用有效正文，档案按版本及来源哈希保存；人物成长用有前态、有原因、有正文证据的事件记录。成长后只重审相关人物，既有来源或成长被历史修订移除时，候选分支重新准备，正式版本仍保持可查。

[实际人物任务书](character-brief.md)、[完整输入](character-input.json)与 [执行范围](character-example.json)通过 CLI 从新项目真实生成。它们展示输入组织，未把小传设计冒充已经写出的小说。

新增工程验证覆盖人物任务幂等、只提交本次人物、伪造/失效来源拒绝、按角色选取资料、误信保留、预算不足诊断、读者首读隔离、对白质量问题触发返修、成长后版本更新、旧分支保留、全书 voice_evolution 审查与完本。成长材料保留尚未吸收的记录，早期已吸收内容如省略会告知范围并提供检索路径。

独立前向验证实际执行 101 次 CLI 调用，跑通两章、成长后仅更新相关人物、档案版本与来源检查、显式 refresh、历史修订来源失效、discard 恢复及两章重写后的修订晋升；本次覆盖范围未发现可复现功能缺陷。[调用记录](character-cli-log.json)保留实际结果。独立验证同样使用合成工程审稿，不是文学盲评。

程序验证的是数据与流程，不自动证明每句对白都符合人物，不计算口癖配额或“性格得分”。本次工程审稿使用明确标记的合成回执；新机制尚无长篇对白质量的统计评价。v1.3 再次审计原有两部真实样本通过，未将其文学结果归功于后来添加的功能。

## v1.4.0 局部返修与发布审查

新增 [段落补丁协议](../references/repairs.md)。简单问题由审稿明确标为 local，返修输入仅提供问题段落及邻段，保留必要约定、状态与历史；整章未来设计不重复传入。补丁绑定不可变基稿哈希和绝对字符位置，全部验证后才合成候选。错误版本、原文错位、越界与重叠均拒收；需要扩大范围时显式申请整章上下文，不重置返修次数。

历史候选修订支持同样的补丁，无需改动的后章支持 reuse_original。两者仍重新抽取事实与摘要、执行整章 facts/reader，原审稿与原偏移不得直接复用。正式分支在整批验证并晋升前保持不变。已派发的旧版完整正文任务继续兼容；局部模式是新增可选回执，不改变旧项目的规划模式。

独立验证完成 53 项前向检查，覆盖事实与读者两条返修路径、相同结果重交、不同结果冲突、候选材料重建、扩大上下文、两章历史修订晋升及发布冻结。[验证日志](patch-independent-log.json)和[补充中断/切片日志](patch-recovery-log.json)记录实际结果；模拟草稿 SQL 写入后中断，确认完整回滚，重启可恢复原任务并重交。独立验证未发现本范围发布阻断。

合成工程样本的 7,586 字符正文仅选入 181 字符摘录；同一项目局部与完整工作包分别为 2,328 / 9,849 JSON 字符，补丁与整章结果分别为 350 / 7,985 JSON 字符。这表示重复输入输出减少，不是实测模型 token、费用或文学质量结论。完整审稿仍需读取合成正文。

另一次[设计完整性审查](release-design-audit.json)实际跑通两卷完本、从首章建立候选修订、重建受影响设计及人物档案、后文复核、晋升与再次完本；原分支正文保持不变。结合已有空间、人物、资源、记忆与恢复测试，本次未发现需要继续扩展架构才能发布的必要缺口。语义判断仍依赖执行模型及审稿，不能把这一结论解释为没有任何潜在缺陷。

v1.4.0 再次审计《借火簿》12 章与《夜班退件》1 章，均通过；未把旧文学样本当作新增补丁机制的效果实验。发布采用本地版本 ZIP、SHA-256 与清单，并对解压后的副本运行完整测试；详见[发布说明](release-1.4.0.md)。

## 真实写作与返修

[《借火簿》第一章](story-v2/export/0001.md)起，共 12 章、4,778 汉字、两个阶段及明确结局。[任务执行记录](story-v2/execution-report.json)确认 79 个已验收任务，包括 2 次规划、12 次执笔、13 次事实审查、13 次读者审稿、1 次返修，以及批次、卷和全书复核。数据库状态为 completed，无未解决审计问题，无开放核心承诺。

这是压缩测试书，合同显式采用 4,000～12,000 汉字；没有降低一部正式百万字小说的既定目标。它展示从开篇到结局的闭环，不能替代百万字实写验收。

首版不自动迁移旧数据库，不自动安装服务、配置账户、发布小说或修改作者约定。无法核实旧模型进程已退出时，宁可保留任务并报告，也不启动重复写手。

## 使用

将整个 skill 文件夹放入目标宿主支持的技能目录，或让模型直接读取 [SKILL.md](../SKILL.md)。宿主需提供文件读写及 Python 3.9+。从少量偏好与试章定调开始；需要独立后台运行时，按 [运行说明](../references/runtime.md)配置自己的通用驱动。

可复核命令：

```bash
python3 scripts/novel.py --help
python3 -m unittest discover -s tests -v
python3 validation/run_story.py --project /absolute/new-validation-project
python3 validation/run_other_genre.py --project /absolute/another-new-validation-project
```

真实试验的本地 SQLite 和全任务文件保留在 `validation/runs/`，压缩交付包不携带这些运行缓存；正文、审稿、结果与可重放脚本包含在包内。
