# v1.4.1 千章连续写作上下文排查

日期：2026-10-02。审查对象：已发布 v1.4.1（Git e95f5c8）。结论：章数增长本身不必把历史全文塞进单次任务，但当前实现存在可复现的材料累积超限与无法自动恢复问题，不能声称已具备千章不中断的上下文保障。

后续状态：上述缺陷已在工作目录 v1.5.0 修复，见[架构修复验收](context-architecture-fix.md)。本报告保留当时测量结果，不代表当前实现。

## 验证范围

[可重放脚本](context_stress.py)在临时目录分别建立三组 1000 章历史，每章 3000 字符（含标点），每组正文共 300 万字符、2,638,107 汉字。启用 layered、profiled、十卷篇幅预算与人物档案，使用真实事件校验、哈希链、工作包生成、输入文件序列化及运行器错误处理。每组事件链均重放一致。

正文是明确标注的机械合成负载；测试直接批量准备历史和合成审稿标记，未通过模型逐章创作及真实语义审稿。它验证数据规模与材料增长，不证明文学质量，也不等于真实无人值守完成 1000 章。未连接模型，未测真实 token、费用或宿主聊天窗口；所有量为 Python 字符数。原始测量在[结果 JSON](context-stress-results.json)。

重放时将脚本复制到 v1.4.1 tag 的隔离副本，执行 `python3 validation/context_stress.py --out /absolute/results.json`。脚本拒绝在新版实现上输出伪称旧版的报告；新版验证用 context_endurance.py。

## 实际结果

默认预算为 48,000 字符。程序按紧凑 JSON 计量，实际 input 文件使用缩进 JSON；下表“输入文件”经过真实 write_json 写盘后读取计量。

| 只推进时钟，核心状态稳定 | 1 | 7,177 | 11,801 | 可生成 |
| 同上 | 1000 | 7,370 | 12,110 | 可生成 |
| 每章新增一条主角认知 | 100 | 31,880 | 50,265 | 程序放行，文件已超过名义预算 |
| 同上 | 200 | 47,373 | 74,521 | 程序放行，文件已超过名义预算 |

| 每章新增且持续积压一条伏笔 | 150 | 46,815 | 77,810 | 程序放行，文件已超过名义预算 |

这里的 200/300 章是采样点，不能推断所有小说都在这些章节失败，也没有定位精确的首次失败章。伏笔场景刻意积压，表示风险暴露条件；正常及时兑现会降低这一路径的增长。

全书复核的分段任务仍只包含一章，实测文件 9,336 字符；1000 段合成覆盖记录后的跨段任务文件 6,446 字符，没有把全书正文或全部覆盖回执一次放入。分段组织限制了初始体积，但后续独立复核发现跨段任务缺少实际分段结论，不能以包小证明审读材料足够；v1.5 已补齐。跨段任务后续主动检索的材料在 v1.4.1 仍不计入初始包限制。

## 已确认的问题

1. **必需状态持续增长，超限后无法自动解包。** [memory.py](../scripts/novel_core/memory.py) 在 profiled 模式中加载相关人物全部认知，计划 topics 不再限制认知范围；全部到期/临期开放伏笔也进入必需部分。人物档案和全书/本卷设计本身完整加载，未建立有界视图。历史全文依赖同样全部加入。必需部分超限便直接抛错，可选摘要的裁剪对此无效。

2. **超限停线，单纯恢复没有修复动作。** 在 1000 条认知的合成书中，为下一章准备事实审查任务，真实 runner 返回 paused/context_overflow，未创建任务、未启动 driver，1000 章历史保留。resume 的数据审计通过并回到 ready，下一次 next 再次 context_overflow。任务派发之前的错误没有进入模型返修或自动材料拆分流程。只调高上限会推迟问题，不能使增长有界。

3. **计量对象和模型实际读取对象不同。** [store.py](../scripts/novel_core/store.py) 的 dump 使用紧凑 JSON，write_json 使用缩进 JSON。[memory.py](../scripts/novel_core/memory.py) 只验证前者；实际文件、重复阅读 brief、Skill 指令、工具回执、追加检索、输出和宿主既有消息都没有统一预算。48,000 字符也不是 48,000 token，不能据此保证适配任意模型窗口。

4. **宿主会话累积不由工作包限制。** 默认配置为 serial。[runtime.md](../references/runtime.md) 要求宿主留出空间、按阶段重读材料并在限制前换会话，但没有确定性的会话剩余额度或轮换门禁。fresh 协议要求真实空会话 ID，工具只能检查声明；外部驱动若复用旧会话，单独启动进程也不能证明模型上下文已清空。主聊天即便只看回执，长期控制循环仍需宿主轮换。此项来自实现/协议审查，未模拟真实模型窗口。

5. **额外检索存在未计入预算的入口。** recall --state 可完整返回派生状态，认知负载的状态已达 178,748 个紧凑 JSON 字符；设计 history、人物 history 同样可全量输出。普通 recall 虽按记录数分页，但不是字符预算，而且默认按历史正序返回；自动人物历史在第 1000 章仍取最早的 1～20 章，本次实际复现。近三章摘要会补充近期情况，但不能代替第 21～997 章的相关旧事，也不能认为未放入包的历史不存在。

## 修复方向及验收条件

- 以真正送入模型的文本为预算对象，支持宿主给出可用额度，并预留指令、检索、输出空间。测量信息如无法获得，明确采用保守字符预算；不能标成实测 token。
- 当前任务必需约束保持完整；认知、人物经历、伏笔、设计按相关实体/话题/因果依赖组织成有来源的工作视图。相关性不能只靠字符串，不能为了缩短输入静默丢掉误信、伤势或关键承诺。
- 长依赖优先提供已校验证据片段和可检索位置；确需全文理解因果时分批审读，持久化覆盖记录和结论。不要直接把所有依赖全文移到另一次仍然超限的请求。
- 在派发前增加材料准备/压缩/分批读取的可恢复任务；必需材料放不下时由有界修复流程处理。resume 不能仅重复失败动作；无法压缩的任务应明确停线原因和所需条件。
- 连续运行以真正独立的 worker 会话为优先，控制层只保留短回执；serial 保留为受宿主能力限制的模式，并提供换会话检查点。重新打开会话必须从持久化状态恢复，不能带回完整历史。
- 回归应同时覆盖认知、伏笔、人物档案、场所连接与历史依赖增长；验证正文、审稿、补读合计预算以及修复后自动继续。再增加真实宿主长跑实验，独立报告工程、会话与创作效果。

## 本次处理状态

本次新增压力测试与排查证据，尚未修改生产代码来修复上述问题，也未改动既有发布 ZIP。此前 100 项通过覆盖其原有场景；原千章测试使用短正文、两个核心人物和几乎不增长的状态，不能据此推导真实长篇上下文始终有界。本报告补充了发布后发现的明确限制。
